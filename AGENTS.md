# Senior-vibecoders — общие правила для всех ИИ-агентов

Хакатон-проект. 3 разработчика, у каждого своя зона и свой ИИ-агент (Claude Code / Codex).
Приоритет: **рабочее демо к дедлайну**. Скорость важнее идеальности, но `main` всегда должен запускаться.

## Структура и владельцы

| Папка       | Стек                                   | Владелец       | Порт |
|-------------|----------------------------------------|----------------|------|
| `frontend/` | React + TypeScript (Vite)              | фронтендер     | 5173 |
| `backend/`  | Python + FastAPI                       | бэкендер       | 8000 |
| `ai/`       | Python-пакет, LLM (OpenAI / NVIDIA)    | ИИ-разработчик | —    |
| `shared/`   | контракт API — `shared/api.md`         | все, по договорённости | — |

Поток данных: `frontend → backend (:8000) → import ai (run_analysis)`. Фронт никогда не ходит в `ai/` напрямую.
Задача и архитектура — в `ARCHITECTURE.md`. Прочитай его перед первой задачей.

Инструкции общие для Claude Code и Codex, файлы не дублируются: этот файл + `AGENTS.md` в папке своей зоны
(`ai/`, `backend/`, `frontend/`). Codex подхватывает его сам; Claude — прочитай `AGENTS.md` своей папки перед работой.
Корневой `CLAUDE.md` — только ссылка на этот файл, правила в него не пишем.

## Жёсткие правила

1. **Работай только в своей папке.** Нужна правка в чужой зоне — не делай её. Опиши, что и кому нужно поменять, и сообщи человеку.
2. **Контракт — `shared/api.md`.** Код обязан ему соответствовать. Меняешь формат запроса/ответа — сначала обнови `api.md` и явно скажи человеку, что контракт изменился (он предупредит команду).
3. **Никого не жди — заглушки.** Фронт — моки по контракту, бэк — заглушка вместо ИИ, ИИ — фиксированный ответ, пока модель не готова. Заглушки удаляются только когда реальная часть работает.
4. **Секреты только в `.env`** (он в `.gitignore`). В репо — только `.env.example` с пустыми значениями. Не выводи ключи в логи, не хардкодь, не вставляй в README.
5. **Без спроса не трогай** корневые файлы: `AGENTS.md`, `CLAUDE.md`, `.gitignore`, корневой `README.md`, `shared/`.
6. **Не тащи тяжёлые зависимости** без необходимости. Новая зависимость — сразу в файл зависимостей своей папки.

## README — обязателен и всегда актуален

Каждый агент **ведёт `README.md` своей папки** и обновляет его в том же коммите, где меняется поведение. Обязательные разделы:

1. **Что это** — 1–2 предложения, роль модуля в системе.
2. **Быстрый старт** — точные команды установки и запуска с нуля (копируй-вставляй, проверенные).
3. **Переменные окружения** — таблица: имя, зачем, пример (без реальных значений).
4. **API / интерфейс** — эндпоинты или функции с примерами запроса и ответа.
5. **Статус** — что работает, что на заглушках, известные баги.
6. **Как проверить** — одна команда или шаги, чтобы убедиться, что всё работает.

README пишется для тиммейта, который видит папку впервые за 10 минут до демо. Коротко и по делу.

## Как агент работает (агентный цикл)

1. **Прочитай контекст перед кодом:** этот файл, `AGENTS.md` своей папки, `shared/api.md`, README своей папки. Не угадывай структуру — посмотри файлы.
2. **Короткий план** (3–7 шагов) для задач сложнее пары строк. Если задача неоднозначна или затрагивает контракт — спроси, а не выдумывай.
3. **Маленькие шаги.** Одно логическое изменение → проверка → коммит. Не переписывай то, что работает.
4. **Проверяй по-настоящему.** После изменения запусти код / тест / curl и посмотри на реальный вывод. Не заявляй «готово», если не проверил. Если не смог проверить — так и скажи.
5. **Не выдумывай API библиотек.** Не уверен в сигнатуре или версии — посмотри установленную версию или документацию.
6. **Ошибка → причина, а не костыль.** Не глуши исключения и не отключай проверки, чтобы «зелёное» стало зелёным.
7. **Отчёт в конце:** что сделано, какие файлы изменены, как проверить, что осталось / что блокирует.

## Хакатонная стратегия

- **Сначала сквозной путь**, потом глубина: фронт → бэк → ИИ должны связаться (хоть на заглушках) как можно раньше.
- **Demo path священен.** Сценарий, который покажем жюри, должен работать всегда. Всё экспериментальное — за флагом или в отдельной ветке.
- **Fallback для демо:** если внешний API (LLM, сеть) упал — показываем заранее подготовленный ответ, а не ошибку.
- **Таймбокс:** если задача не поддаётся 30–40 минут — остановись, сообщи человеку, предложи упрощение.
- **Feature freeze за 2–3 часа до конца:** только багфиксы, README, полировка демо.
- Перед демо: `git tag demo-vN` на рабочей версии.

## Git

- `main` всегда рабочий. Ветки короткие: `front/<фича>`, `back/<фича>`, `ai/<фича>`.
- Перед пушем: `git pull --rebase origin main`, убедись, что твоя часть запускается.
- Мёрж в `main` часто — каждые 1–2 часа. Долгие ветки = конфликты в финале.
- Сообщения коммитов: `<зона>: <что сделано>`, например `ai: add NVIDIA fallback`.
- Никогда: `git push --force` в `main`, коммит `.env`, `node_modules/`, `.venv/`, весов моделей, больших датасетов.
