# Архитектура: ИИ-агент «Анализ организационной структуры и функционала»

## 1. Что строим (из ТЗ)

Пользователь загружает комплект документов **«до»** и **«после»** реорганизации → агент:
1. определяет подразделения: **сохранены / созданы / упразднены / преобразованы**;
2. сопоставляет функции «до» → «после», находит **потерю функций**;
3. сравнивает функции подразделений между собой → **дублирование** и **конфликт интересов**;
4. к **каждому** выводу даёт источник: документ + пункт + цитата;
5. формирует итоговое заключение.

Жёсткое ограничение ТЗ: **никаких утверждений без подтверждения документами**. Это главный принцип архитектуры.

Критерии: работоспособность 25, техреализация/agentic AI 25, **README и воспроизводимость 25**, ценность 15, оригинальность 10.

## 2. Что показывают тестовые документы (ред. 8 → ред. 9 Положения о ВА)

- Ред. 8, п. 3.4: в БВА входят **ДНМ, ДККМ** + должность «Директор направления внутреннего аудита» с подчинёнными.
- Ред. 9, п. 3.4: **ДИТААД** (ИТ-аудит и анализ данных) и **ДОА** (операционный аудит) — **созданы**; ДНМ, ДККМ — **сохранены**; «Директор направления внутреннего аудита» — **упразднён/преобразован**.
- Состав должностей ДККМ изменился (п. 3.8 → 3.9): исчезли «Директор по контролю качества аудита и методологии», «Менеджер по аудиту».
- Функции описаны в основном в разд. 2 (функции БВА в целом) и разд. 5 (права/обязанности по ролям, напр. п. 5.3 «Директоры департаментов и Директоры направлений ДИТААД и ДОА»).
- Нумерация пунктов написана текстом («3.4.», «2.4.7.») → пункты можно вырезать детерминированно, без LLM.
- Размер: ~84 тыс. символов на документ (~25–30 тыс. токенов) → документ целиком влезает в контекст современной модели.

Это и есть наш golden-тест: агент обязан найти ДИТААД/ДОА как созданные, изменение ДККМ и дать ссылки на п. 3.4–3.9.

## 3. Общая схема

```
┌──────────────┐  multipart   ┌───────────────────────┐  import   ┌──────────────────────────┐
│  frontend    │ ───────────► │ backend (FastAPI:8000)│ ────────► │ ai (python-пакет)        │
│ React + TS   │ ◄─────────── │ загрузка, задачи,     │ ◄──────── │ run_analysis(before,     │
│ upload/прогресс│  polling    │ статус, результат,    │ progress  │   after, on_progress)    │
│ /результаты  │   JSON       │ экспорт отчёта        │ callback  │ → AnalysisResult         │
└──────────────┘              └───────────────────────┘           └──────────────────────────┘
                                         │                                   │
                                   storage/ (файлы,                   OpenAI / NVIDIA API
                                   результаты JSON)
```

**Решение:** `ai/` — это Python-пакет, который бэкенд импортирует (`pip install -e ../ai`), а не отдельный HTTP-сервис.
Причина: анализ идёт минуты, нужен прогресс по шагам — через callback это тривиально, через второй HTTP-сервис — лишняя сложность.
Для автономной работы у `ai/` есть CLI: `python -m ai.cli before/*.docx --after after/*.docx` → JSON.

## 4. ИИ-часть (ai/) — пайплайн агента

Принцип: **детерминированный скелет + LLM там, где нужно понимание текста + проверка каждой ссылки кодом.**

| # | Шаг | Как | LLM? |
|---|-----|-----|------|
| 1 | **Парсинг** | DOCX — `python-docx`, PDF — `pymupdf`, XLSX — `openpyxl`. Сохраняем порядок абзацев и таблицы. | нет |
| 2 | **Нарезка на пункты** | Regex по нумерации (`^\d+(\.\d+)*\.`), подпункты «а.», «б.». Каждый пункт: `clause_id`, `doc_id`, `section`, `text`. | нет |
| 3 | **Извлечение подразделений** | Из разделов о структуре: название, аббревиатура, подчинение, должности + `clause_id`. Structured output (JSON-схема). | да |
| 4 | **Сопоставление подразделений до/после** | Сначала точное совпадение по названию/аббревиатуре, затем LLM решает спорные: `preserved / renamed / created / abolished / merged / split / transformed` + обоснование. | да |
| 5 | **Извлечение функций** | Функции/обязанности с привязкой к подразделению/роли и пункту. | да |
| 6 | **Сопоставление функций** | Эмбеддинги → для каждой функции «до» top-k кандидатов «после» → LLM-верификация: `preserved / moved / modified / lost`. | да |
| 7 | **Дублирование** | Попарная близость функций разных подразделений «после» выше порога → LLM подтверждает дубль. | да |
| 8 | **Конфликт интересов** | Чек-лист принципов разделения обязанностей (проверяющий = исполнитель; методология + контроль качества собственной методологии; консультирование + аудит одной области и т.п.) → LLM применяет к функциям. | да |
| 9 | **Валидатор источников** | Каждая цитата проверяется **кодом**: есть ли она (нормализованно) в тексте указанного пункта. Нет → вывод помечается `unverified` и не попадает в заключение. | нет |
| 10 | **Заключение** | LLM пишет итог **только** из проверенных находок (markdown). | да |

Почему это «agentic»: оркестратор ведёт многошаговый процесс, каждый шаг — инструмент с чётким входом/выходом, есть самопроверка (шаг 9) и повторная попытка при невалидном JSON. Опционально (если останется время): чат-агент с tool calling (`search_clauses`, `get_clause`, `compare_units`) для вопросов пользователя по документам.

Модели и провайдеры:
- Один клиент `call_llm()`; провайдер через `LLM_PROVIDER` (`openai` | `nvidia`), модели через env. Конкретные модели выбираем по списку, доступному в кабинете.
- Эмбеддинги — через OpenAI; кэш на диск, чтобы не платить повторно.
- Температура 0, structured output, валидация Pydantic, 1 ретрай.

Структура:
```
ai/
  ai/__init__.py
  ai/pipeline.py      ← run_analysis(...) — оркестратор шагов 1–10
  ai/parsing.py       ← шаги 1–2
  ai/units.py         ← шаги 3–4
  ai/functions.py     ← шаги 5–8
  ai/evidence.py      ← шаг 9
  ai/report.py        ← шаг 10
  ai/llm.py           ← call_llm, embeddings, провайдеры, кэш
  ai/schemas.py       ← Pydantic-модели = контракт
  ai/prompts/*.md
  ai/cli.py
  evals/golden_r8_r9.json  ← ожидаемые находки для тестовых документов
  pyproject.toml, README.md, .env.example
```

## 5. Backend (backend/, FastAPI :8000)

Роль: приём файлов, запуск анализа в фоне, отдача статуса/результата, экспорт.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health` | проверка |
| POST | `/api/analyses` | multipart: `before[]`, `after[]` (docx/pdf/xlsx) → `{ "id": "..." }`, запускает фоновую задачу |
| GET | `/api/analyses/{id}` | `{ status: queued/running/done/failed, step, progress, error }` |
| GET | `/api/analyses/{id}/result` | `AnalysisResult` (схема ниже) |
| GET | `/api/analyses/{id}/documents/{doc_id}/clauses/{clause_id}` | полный текст пункта для панели «Источник» |
| GET | `/api/analyses/{id}/report.docx` | экспорт заключения (опционально) |
| POST | `/api/analyses/demo` | запуск на встроенном комплекте ред. 8/9 — для демо в один клик |

Реализация:
- Фоновые задачи: `BackgroundTasks` или `asyncio.to_thread`; хранение — папка `storage/<id>/` (исходники + `result.json` + `status.json`). Без БД — хватит.
- `AI_MOCK=true` → вместо `run_analysis` отдаётся фиксированный `AnalysisResult` из `mocks/result.json` (фронт может работать сразу).
- Зависимости: добавить `python-multipart` (загрузка файлов), `python-docx` (экспорт).

## 6. Frontend (frontend/, React + TS)

Экраны:
1. **Загрузка** — две зоны «До реорганизации» / «После», список файлов, кнопка «Анализировать», кнопка «Демо-комплект».
2. **Прогресс** — шаги пайплайна с галочками (опрос статуса раз в 1–2 с).
3. **Результат** — вкладки:
   - **Заключение**: итог + счётчики (создано / упразднено / потерь / дублей / конфликтов).
   - **Подразделения**: таблица «до → после» со статус-бейджами.
   - **Функции**: таблица сопоставления (функция, где была, куда ушла, статус, уверенность).
   - **Риски**: карточки потерь, дублей, конфликтов интересов с рекомендацией.
   - У каждого вывода кнопка **«Источник»** → боковая панель: документ, пункт, текст с подсветкой цитаты.
4. Плашка: «Выводы носят рекомендательный характер и требуют проверки ответственным сотрудником».

Стек: Tailwind + shadcn/ui (таблицы, вкладки, бейджи, sheet), TanStack Query (опрос статуса), типы из `shared/api.md`.

## 7. Контракт данных (кратко; полная версия — shared/api.md)

```ts
type Side = "before" | "after";

interface Evidence {
  doc_id: string; doc_name: string; side: Side;
  clause_id: string;      // "3.4"
  quote: string;          // точная цитата из пункта
  verified: boolean;      // прошла проверку кодом
}

interface Unit {
  id: string; side: Side; name: string; abbr?: string;
  parent?: string; positions: string[]; evidence: Evidence[];
}

interface UnitChange {
  before_unit_ids: string[]; after_unit_ids: string[];
  status: "preserved" | "renamed" | "created" | "abolished" | "merged" | "split" | "transformed";
  rationale: string; evidence: Evidence[];
}

interface FunctionMapping {
  function: string; before_unit_id?: string; after_unit_ids: string[];
  status: "preserved" | "moved" | "modified" | "lost";
  confidence: number; evidence: Evidence[];
}

interface Finding {
  id: string;
  type: "function_loss" | "duplication" | "conflict_of_interest" | "structure_change";
  severity: "high" | "medium" | "low";
  title: string; description: string; recommendation?: string;
  unit_ids: string[]; evidence: Evidence[];
}

interface AnalysisResult {
  units: Unit[]; unit_changes: UnitChange[];
  function_mappings: FunctionMapping[]; findings: Finding[];
  conclusion_md: string;
  meta: { model: string; provider: string; duration_s: number; documents: { doc_id: string; name: string; side: Side }[] };
}
```

**Первое действие команды:** согласовать эту схему и положить `mocks/result.json` — пример на данных ред. 8/9. Дальше все трое работают параллельно.

## 9. Замечания по текущему репо

- `backend/requirements.txt` в кодировке **UTF-16** (результат `pip freeze >` в PowerShell) → git считает его бинарным, диффы не видны. Пересохранить в UTF-8: `pip freeze | Out-File -Encoding utf8 requirements.txt`.
- Корневой `.gitignore` игнорирует `data/`, `models/`, `outputs/`:
  - тестовые документы **нельзя** класть в `data/` — они не попадут в репо, а воспроизводимость = 25 баллов. Кладём в `samples/`;
  - если бэкенд назовёт пакет `app/models/` — он тоже будет проигнорирован. Называть `app/schemas/` или сузить правило до `/models/`.
- Нет корневого README и `shared/api.md` — README оценивается на 25 баллов, начать его сразу.
